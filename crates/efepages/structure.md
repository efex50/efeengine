# efepages

`efepages` is a sparse, paged byte memory used by the `efescript` scripting VM. A `Page` holds a map from page index to a fixed-size byte buffer, so only pages that were actually written consume memory, and reads from untouched memory return zeros. The page size is a compile-time constant (`PAGE_SIZE`, default 4096) generated by the helper proc-macro crate `page_size_macro`.

## Main concepts
- **`Page`** (`page/mod.rs:10-15`): fields `pagesize: usize` (private), `pub page: PageMap`, `max_pages: Option<usize>` (private, always `None` today). `PageMap` is `HashMap<usize, Vec<u8>, BuildHasherDefault<NoHashHasher<usize>>>`, keyed by page (sector) index.
- **Construction**: `Page::default()` uses `PAGE_SIZE`; `Page::new_with_custom_pagesize(n)` (`init.rs:9`) uses a custom page size, with no max-pages limit.
- **Address mapping** (`funs.rs:164`, `get_vars`): for an address `a`, sector = `a / pagesize`, offset within the page = `a % pagesize`. The function returns the start sector, the start offset, and the last sector touched by the range `[a, a+len)`.
- **Reads** (`funs.rs:99`, `read(start, len) -> Vec<u8>`): the range is split into per-page slices. If a page is present its bytes are copied; if it is absent, zeros are produced. Nothing is allocated by a read.
- **Writes** (`funs.rs:27`, `write(start, Vec<u8>)`): the data is split into per-page chunks (`get_writepages`, `funs.rs:51`). A page that does not exist yet is created by `create_new_page` as a zero-filled buffer of `pagesize` bytes, so this is the implicit "allocation" step. Pages are never freed.
- **`PAGE_SIZE`** (`vars.rs`): produced at compile time by `page_size!()`. `page_size_macro` reads the environment variable `efepage_size` (default `"4096"`) and emits it as the constant. Because the value comes from the environment during macro expansion, Cargo does not track it; a changed value takes effect only after `efepages` is rebuilt (e.g. `cargo clean -p efepages`).
- **Allocation policy**: efepages does not allocate or manage addresses itself. The efescript allocator (`crates/efescript/src/runtime/allocator`) works on top of `Page` through raw pointers.

```rust
use efepages::page::Page;

let mut mem = Page::default();          // PAGE_SIZE bytes per page
mem.write(20, vec![255; 500]);          // allocates the pages it touches
let bytes = mem.read(20, 500);          // Vec<u8> of length 500
assert_eq!(bytes.len(), 500);
let untouched = mem.read(1_000_000, 4); // zeros, nothing allocated
```

## Public API
- `efepages::vars::PAGE_SIZE: usize` - compile-time page size (4096 unless `efepage_size` is set at build time).
- `efepages::page::Page` - the sparse paged memory (`#[derive(Debug)]`).
- `efepages::page::PageMap` - `HashMap<usize, Vec<u8>>` type alias with the identity hasher.
- `Page::default()` - new empty memory with `PAGE_SIZE` pages.
- `Page::new_with_custom_pagesize(pagesize: usize) -> Page` - new empty memory with a custom page size.
- `Page::write(&mut self, start: usize, write: Vec<u8>)` - writes bytes at an address, allocating pages as needed.
- `Page::read(&self, start: usize, len: usize) -> Vec<u8>` - reads bytes; absent pages read as zeros.
- `pub page: PageMap` field - direct access to the page map (efescript reads `.page.len()` for a RAM estimate).
- `page_size_macro::page_size!` - proc macro (internal helper; used by `vars.rs`).

## Status and known gaps
- `set_max_pages` is `todo!()`: `crates/efepages/src/page/init.rs:14-16`. Calling it panics.
- `create_new_page` has an inverted check: `init.rs:21` tests `max < self.page.len()` and should test `len < max`. The "Maximum pages reached" panic at `init.rs:23` is effectively unreachable today because `max_pages` is always `None` (no safe way to set it).
- Boundary bug in `write`: when a write ends exactly on a page boundary and spans more than one page, the final chunk is computed as `tail % pagesize == 0`, so the last page's data is dropped (`funs.rs:79-81`). Verified: `write(0, vec![7; 2*PAGE_SIZE])` leaves page 1 all zeros.
- Same boundary bug in `read`: `read(0, 2*PAGE_SIZE)` returns only `PAGE_SIZE` bytes (`funs.rs:124-125`, verified).
- Zero-length operations at a page boundary: `write(PAGE_SIZE, vec![])` panics with a slice index error (`funs.rs:71`, slice `write[counter..counter_end]`; verified). `read(PAGE_SIZE, 0)` returns `PAGE_SIZE` zero bytes instead of an empty vector (`funs.rs:110-134`; verified).
- No free / unmap of pages; memory only grows.
- `read` and `write` have no bounds on address arithmetic beyond `usize` overflow (`start + len` may overflow for huge values).
- Unit tests in `src/lib.rs` are mostly `println!` checks, with a single assertion (`pt8`); they do not check the boundary cases above.
